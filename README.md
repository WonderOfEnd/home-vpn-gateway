# home-vpn-gateway

Превращает домашний сервер в прозрачный шлюз для всей локальной сети: весь
трафик идёт через туннель VLESS+REALITY на внешний сервер, кроме российских
сайтов/сервисов — они идут напрямую. DNS резолвится через тот же туннель,
чтобы провайдер не мог подменять ответы.

На роутере в DHCP прописывается шлюз и DNS — этот сервер, дальше всё
происходит само.

## Что нужно на стороне внешнего сервера (не входит в этот репозиторий)

Рабочий инстанс [3x-ui](https://github.com/MHSanaei/3x-ui) с VLESS-инбаундом:
`network: tcp`, `security: reality`, **без** `flow` у клиента (Mux и
`xtls-rprx-vision` несовместимы — см. ниже), **без** `mldsa65Seed`
(пост-квантовый REALITY требует очень свежее ядро клиента — не стоит того
здесь). Создайте отдельного клиента специально под этот шлюз (не
переиспользуйте UUID телефона/приложения). Из данных клиента понадобятся:
IP сервера, UUID клиента, публичный ключ REALITY, short ID, server name
(SNI/домен маскировки).

## Структура

```
xray/config.json                    конфиг xray-клиента (вся логика шлюза)
systemd/xray.service                запускает xray от пользователя `nobody`
                                     с CAP_NET_ADMIN (нужно для TPROXY)
systemd/xray-tproxy-route.service   policy routing для TPROXY (сейчас не используется, см. ниже)
iptables/rules.txt                  актуальный набор правил, в формате iptables-restore
pihole/NOTES.md                     единственная настройка Pi-hole, которая здесь важна
```

## Установка

1. Установить xray-core (`bash -c "$(curl -L https://github.com/XTLS/Xray-install/raw/main/install-release.sh)"`).
2. Скопировать `xray/config.json` в `/usr/local/etc/xray/config.json`,
   заполнить `<VPS_IP>`, `<CLIENT_UUID>`, `<REALITY_SERVER_NAME>`,
   `<REALITY_PUBLIC_KEY>`, `<REALITY_SHORT_ID>` из панели.
3. Скопировать `systemd/xray.service` (и `xray-tproxy-route.service`, если
   нужен) в `/etc/systemd/system/`, выполнить `systemctl daemon-reload`,
   `systemctl enable --now xray`.
4. Применить `iptables/rules.txt` (сначала заполнить `<VPS_IP>`), затем
   сохранить на диск (`iptables-persistent` / `netfilter-persistent save`
   или аналог в вашем дистрибутиве), чтобы правила пережили перезагрузку.
5. Настроить upstream Pi-hole на `127.0.0.1#5353` (см. `pihole/NOTES.md`).
6. Прописать на роутере DHCP-шлюз и DNS — LAN-адрес этого сервера.

Включить IP forwarding (`net.ipv4.ip_forward=1`), если ещё не включён.

## Как маршрутизируется трафик

- **DNS** (запрос на любой адрес:53 из локальной сети) → редиректится на
  локальный Pi-hole → Pi-hole форвардит на `127.0.0.1:5353` (xray) →
  туннелируется на внешний сервер → резолвится уже там. Это осознанное
  решение: при резолве на месте провайдер подменял ответы для конкретных
  доменов (зафиксировано напрямую — см. `pihole/NOTES.md`).
- **TCP** из локальной сети → `iptables` делает `REDIRECT` на xray'вский
  `redirect-in` (12345) → маршрутизация по IP/домену назначения:
  - приватные диапазоны, собственный IP внешнего сервера → `direct`
    (чтобы не проксировать прокси через себя же)
  - российские IP-диапазоны / `geosite:category-ru` / яндекс / vk / mailru
    / `.ru` / `.su` / `.рф` → `direct`
  - всё остальное → `proxy` (туннель VLESS/REALITY, с мультиплексированием)
- **UDP** из локальной сети → **не туннелируется** (см. ниже). Только
  собственный upstream-запрос Pi-hole идёт через отдельный релей без
  TPROXY (`dns-in`, фиксированная цель `8.8.8.8:53` — `followRedirect` не
  нужен, так как назначение статично).

## Почему UDP не туннелируется

В репозитории есть полноценная настройка TPROXY для обычного UDP
(`tproxy-udp-in`, цепочка `XRAY_UDP` в mangle, policy routing через
`ip rule`/`ip route`, юнит `xray-tproxy-route.service`) — всё это
присутствует, но **не подключено** (хук
`iptables -t mangle -A PREROUTING ... -j XRAY_UDP` закомментирован/убран).

Причина: real-time UDP (WebRTC — голос в Discord, видеозвонки, игры с
ICE/STUN) плохо переживает мультиплексирование через TCP-туннель.
Наблюдаемый симптом: голосовой канал в Discord зависал в цикле
"подключение → маршрут не установлен → переподключение". Первопричина:
проверки STUN/ICE-кандидатов частично проходили через связку
TPROXY+Mux (несогласованное сопоставление исходящих портов при повторных
попытках ломает требование ICE к стабильности), из-за чего клиент так и
не переключался чисто на собственный TCP-фолбэк.

После полного отключения UDP TPROXY трафик из локальной сети просто не
проксируется — а значит, честно и быстро проваливается для всего, что
заблокировано на уровне провайдера (именно так в РФ блокируется голосовой
UDP Discord), и **именно этот чистый быстрый провал заставляет клиента
сразу переключиться на свой TCP-фолбэк**. TCP-трафик `discord.media`
по-прежнему идёт через туннель как обычно (это TCP, обрабатывается тем же
`redirect-in`, что и всё остальное) — именно он и переносит голос.

Компромисс: HTTP/3 (QUIC) и всё, что работает только через UDP, будет
молча откатываться на TCP или просто не работать напрямую без прокси для
клиентов локальной сети — это приемлемо, поскольку браузеры и так
автоматически повторяют попытку через TCP, а на практике это оказалось
надёжнее, чем пытаться туннелировать UDP при нескольких одновременных
устройствах.

Более точечная попытка (обходить туннель только для диапазона STUN-портов
Google, `19300-19309`, оставив полный UDP TPROXY для всего остального —
эти правила всё ещё присутствуют как неиспользуемые в `iptables/rules.txt`)
сработала *нестабильно*: Discord пробует несколько ICE-кандидатов, и через
этот диапазон портов шёл только один из них, так что гонка условий
никуда не делась. Вывод для тех, кто захочет повторить точечный обход:
нужно перекрыть *все* STUN/TURN-кандидаты клиента, а не один.

## Почему Mux, и почему не `xtls-rprx-vision`

Без Mux каждое проксируемое соединение (каждый под-ресурс на каждой
странице, с каждого устройства в сети) открывает новый REALITY-хендшейк на
внешний сервер с нуля. Под реальной нагрузкой с нескольких устройств это
доходило до 250+ одновременных хендшейков и начинало падать (`REALITY:
processed invalid connection ... failed to read client hello` на сервере —
клиент не успевал завершать хендшейки при такой конкурентности). Mux
(`concurrency: 256`) схлопывает это в небольшое число реальных
TCP-соединений.

`xtls-rprx-vision` (настройка `flow`) и Mux взаимно несовместимы —
включение обоих ломает мультиплексированный поток (ошибки вида
`common/mux: unexpected network TCP`). Раз Mux здесь обязателен, `flow` у
этого клиента шлюза не задан. (Клиент на телефоне, который не идёт через
этот шлюз и не нуждается в Mux, может безопасно использовать vision.)

## Рабочий базовый вариант, к которому можно вернуться

Если проблемы с UDP/WebRTC всплывут снова, а гоняться за точечными фиксами
не хочется — этот конфиг *и есть* TCP-only базовый вариант. Именно эта
конфигурация была проверена и подтверждена рабочей (включая голос в
Discord) одновременно на ПК/ноутбуке/телефонах/ТВ.
